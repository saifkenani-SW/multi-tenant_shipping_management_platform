01 — احفظ هذا أولاً

ما هو المشروع؟

هو Modular Monolith مبني بـ NestJS لإدارة عمليات الشحن لشركات متعددة: العميل يطلب شحنة، النظام يولّد عروض أسعار بحسب المناطق، الشركة تقبل الطلب، ينشئ الموظف الشحنة وطرودها وفاتورتها، ثم تُنقَل الطرود في رحلات وبيانات شحن، وأخيراً يُسجَّل إثبات التسليم والدفع.

جواب تسليم جاهز: اخترنا Multi-Tenancy لأن المنصة تخدم شركات شحن متعددة من تطبيق واحد. العزل يكون منطقياً عبر tenant_id، وصلاحيات المستخدم وسياق الطلب يمنعان مستخدم شركة من رؤية أو تعديل بيانات شركة أخرى.
تصحيح مهم جداً: لا تقل إن المشروع يستخدم TypeORM. لا توجد حزمة أو import لـ typeorm في الـ backend. الموجود فعلياً هو Prisma 7 للكتابة وKysely للقراءة والاستعلامات المركّبة. المقارنة مع TypeORM موجودة لاحقاً لأن السؤال وارد في المناقشة.

من هم المستخدمون؟

مالك المنصة، مالك/مدير الشركة، الموظف، السائق، والعميل.

ما الذي تديره الشركة؟

الفروع والمستودعات والمناطق والأسعار والموظفون والمركبات والشحنات.

ما الذي يحمي البيانات؟

JWT، صلاحيات، سياسات Authorization، سياق request، وقيود قاعدة البيانات.

طبقات الكود

Controller
يستقبل HTTP ويرسل الطلب للخدمة؛ لا يضع منطق العمل الثقيل.
Service
ينفذ use case وقواعد العمل والتنسيق بين الموديولات.
Domain Entity
يحرس انتقالات الحالة المهمة، مثل منع إلغاء شحنة بعد dispatch.
Repository
طبقة الوصول للبيانات: Prisma للكتابة وKysely للقراءة.
Facade
البوابة المسموح بها بين الموديولات؛ تقلل الترابط المباشر.

التقنيات الموجودة فعلياً

NestJS 11 TypeScript PostgreSQL 16 + PostGIS Prisma 7 Kysely Redis cache JWT + Passport + bcrypt CASL Firebase Admin Docker Compose Flutter + Riverpod + GoRouter

Prisma schema كذلك يولّد types لـ Kysely؛ أي أن الاثنين متصلان بنفس تعريف البيانات، وليس عندك جدولان منفصلان لكل ORM.

الدقة في جواب العزل: العزل هنا على مستوى التطبيق عبر tenant_id وPrincipal والسياسات وvisibility scopes. لم يظهر في schema أو migrations الحالية استخدام PostgreSQL Row-Level Security، لذلك لا تقل إن قاعدة البيانات تفرض RLS بنفسها.

04 — الفكرة الأهم: العزل والأمان

كيف يضمن المشروع أن كل شركة ترى بياناتها فقط؟

Multi-Tenancy في البيانات

tenant يمثل شركة الشحن. أغلب جداول الشركة تحمل tenant_id: موظفون، فروع، مركبات، أسعار، شحنات، طرود، فواتير، إلخ.

هذا يسمى shared database, shared schema مع عزل منطقي: نفس قاعدة البيانات والجداول، لكن كل صف يخص tenant محدداً.

Multi-Tenancy في الطلب

GlobalAuthGuard يقرأ JWT، ثم يبني Principal داخل AsyncLocalStorage (Request Context). السياسات والخدمات تستخدم هذا السياق لتقرر من يرى أو يعدّل ماذا.

الصلاحية ليست مجرد إخفاء زر في الواجهة؛ هي تحقق backend قبل تنفيذ العملية.

مسار الدخول باختصار

1Login

يتحقق من البريد وكلمة المرور بـ bcrypt.

←
2اختيار profile

إن كان للمستخدم أكثر من دور/شركة، يحصل أولاً على session token مؤقت.

←
3JWT

يحمل user id وtype وtenant/profile/session عند الحاجة.

←
4Principal + Policy

الحارس يبني Principal؛ Decorator @Authorize يفحص السياسة.

المفهوم معناه في المشروع مثال مهم
Authentication من أنت؟ إثبات الهوية عبر JWT بعد login. هل token صالح لمستخدم حقيقي؟
Authorization هل يسمح لك بفعل معين على مورد معين؟ هل هذا الموظف يستطيع تغيير حالة هذا الطرد؟
Role / Permission دور الشركة يتصل بصلاحيات عبر جداول وسيطة. Role مدير ↔ Permission تعديل شحنة.
Visibility Scope ما السجلات التي يحق للمستخدم رؤيتها في القائمة. موظف فرع يرى نطاق فرعه، لا كل الفروع.
Capabilities ما الأفعال المتاحة على سجل أعيد للواجهة. يمكنه view لكن لا يمكنه cancel.
05 — قاعدة البيانات

كل الجداول: 45 model في schema الحالية

هذه ليست قائمة أسماء للحفظ؛ اقرأها كمجموعات أعمال. اسم الجدول بالإنكليزي مطابق لـ backend/prisma/schema.prisma. الحقول المذكورة هي المفاتيح التي تشرح الهدف والعلاقة، وليست كل الأعمدة.

كيف تقرأ العلاقات؟ tenant_id يعني “هذا السجل تابع لشركة”. الحقل الذي ينتهي بـ _id يكون غالباً Foreign Key. جدول مثل role_permission هو جدول ربط many-to-many بين role وpermission.

البحث يعمل على اسم الجدول وشرحه وعلاقاته.

1) الهوية والعملاء والـ tenant — 10 جداول
users

حساب المستخدم الأساسي

يحفظ: email وphone وpassword_hash وتواريخ الإنشاء.

يرتبط بـ: customer_profile وemployee وplatform_admin والجلسات والإشعارات.

platform_admin

مشرف المنصة

يحفظ: حساب المستخدم، الاسم، ودور المنصة مثل SUPER_ADMIN.

العلاقة: واحد إلى واحد تقريباً مع users عبر user_id الفريد.

tenant

شركة الشحن / المستأجر

يحفظ: الاسم والتواصل والشعار والضريبة والحالة.

العلاقة: هو جذر بيانات الشركة؛ تتبعه الشحنات والفروع والموظفون والأسعار.

tenant_owner

ربط مالك بحساب شركة

يحفظ: tenant_id وuser_id وis_primary.

العلاقة: يمنع تكرار نفس المستخدم كمالك لنفس الشركة عبر unique مركب.

customer_profile

ملف العميل

يحفظ: الاسم والهاتف وصورة الملف.

العلاقة: user واحد له profile واحد؛ العميل قد يكون مرسلاً أو مستلماً.

customer_address

عناوين العميل

يحفظ: label والعنوان ونقطة جغرافية geometry(Point, 4326).

العلاقة: عناوين متعددة لملف عميل واحد، مع GiST index للموقع.

customer_tenant

علاقة العميل بالشركة

يحفظ: متى تعامل العميل لأول مرة مع الشركة.

العلاقة: جدول ربط many-to-many بين customer_profile وtenant.

user_session

جلسة Refresh Token

يحفظ: refresh token بشكل hash وexpiry ومعلومات جهاز اختيارية.

العلاقة: جلسات متعددة للمستخدم؛ حذفها عند logout أو عند token مشبوه.

user_device_token

توكن جهاز للإشعارات

يحفظ: FCM token والمنصة android/ios/web.

العلاقة: توكنات متعددة للمستخدم، لكن لا يكرر نفس التوكن لنفسه.

audit_log

سجل التدقيق

يحفظ: من فعل ماذا وعلى أي entity، IP، القيم القديمة والجديدة بصيغة JSON.

العلاقة: قد يرتبط بمستخدم وtenant، وكلاهما اختياري للسماح بأحداث عامة.

2) الاشتراك وإعدادات الشركة — 7 جداول
subscription_plan

خطة الاشتراك

يحفظ: حدود الفروع والمستودعات والموظفين والمركبات والأسعار.

العلاقة: الخطة عامة للمنصة، وتستخدمها اشتراكات شركات عديدة.

tenant_subscription

اشتراك الشركة الحالي/التاريخي

يحفظ: tenant، الخطة، الحالة، البداية والانتهاء وsnapshot للحدود.

لماذا snapshot؟ كي لا تتغير شروط اشتراك قديم عند تعديل الخطة لاحقاً.

tenant_subscription_history

سجل تغيّر الاشتراك

يحفظ: العملية، الخطة السابقة والجديدة، المنفّذ والملاحظات.

العلاقة: يتبع اشتراكاً وشركة وخططاً.

tenant_delivery_settings

إعدادات التسليم

يحفظ: هل OTP أو توقيع أو صور إثبات مطلوبة، وهل يسمح بمندوب.

العلاقة: إعدادات one-to-one للشركة؛ المفتاح هو tenant_id نفسه.

tenant_operational_settings

إعدادات التشغيل

يحفظ: prefix التتبع وقواعد إغلاق/إعادة فتح الشحنة وصلاحية العرض.

العلاقة: one-to-one مع tenant.

tenant_pricing_settings

إعدادات التسعير

يحفظ: volumetric_divisor والعملة الافتراضية.

لماذا مهم؟ يدخل في حساب الوزن الحجمي وسعر العرض.

handling_fee_rule

رسوم المناولة الخاصة

يحفظ: رسوم لكل نوع مثل fragile أو hazardous أو perishable.

العلاقة: unique مركب يمنع تكرار قاعدة لنفس الشركة ونوع الرسوم.

3) الموظفون والصلاحيات — 6 جداول
employee

موظف الشركة

يحفظ: employee_code والاسم والحالة والحساب التابع له.

العلاقة: الموظف تابع لشركة؛ user واحد لا يتكرر كموظف لنفس tenant.

employee_assignment

تعيين موظف في وحدة تنظيمية

يحفظ: الموظف والفرع/المستودع والحالة.

العلاقة: employee قد يعمل في أكثر من unit، لكن لا يكرر نفس التعيين.

assignment_role

دور داخل التعيين

يحفظ: role_id لتعيين موظف محدد في وحدة محددة.

الفكرة: الدور قد يختلف حسب الفرع، لا حسب الموظف عالمياً فقط.

role

دور داخل الشركة

يحفظ: الاسم والوصف وis_active، والاسم unique داخل tenant.

مثال: مدير فرع، محاسب، عامل مستودع.

permission

صلاحية ذرّية

يحفظ: resource وaction ووصف؛ مثل shipment:read أو invoice:record-payment.

العلاقة: تُمنح للأدوار، لا مباشرة للموظف في هذا التصميم.

role_permission

ربط الدور بالصلاحيات

يحفظ: role_id وpermission_id فقط.

العلاقة: جدول many-to-many مع unique مركب لمنع التكرار.

4) المواقع، الفروع، والمناطق — 4 جداول
global_location

هرم المواقع الجغرافي العام

يحفظ: name وtype (country/governorate/city...) وparent_id ونقطة جغرافية.

الفكرة: ليس تابعاً لشركة؛ هو قاموس مواقع مشترك لكل المنصة.

organization_unit

وحدة تنظيمية للشركة

يحفظ: فرع/مستودع/HUB/Locker، parent_id وtree_path وموقع وإعداد zone.

العلاقة: شجرة وحدات لكل tenant؛ ltree يساعد في الاستعلام الهرمي.

org_unit_location_mapping

تغطية الوحدة للمواقع

يحفظ: أي global location يغطيه الفرع ونوع التغطية delivery/pickup/both.

الفكرة: هذا ما يساعد على معرفة الفروع القادرة على خدمة طلب ما.

tenant_zone

منطقة تسعير داخل الشركة

يحفظ: اسم ووصف وحالة المنطقة.

العلاقة: تربط بالفروع وبمصفوفة أسعار الطريق.

5) طلب الشحن والتسعير — 3 جداول
zone_pricing_matrix

مصفوفة سعر المسار

يحفظ: origin_zone وdestination_zone وservice_level والسعر الأساسي ووزن الأساس.

قيد مهم: unique على tenant + الأصل + الوجهة + مستوى الخدمة.

shipment_request

طلب العميل قبل التنفيذ

يحفظ: بيانات المرسل والمستلم والمواقع والوزن والأبعاد والحالة.

العلاقة: يخص customer وقد يولّد quotations متعددة ويصبح shipment لاحقاً.

quotation

عرض السعر

6) الشحن والطرود والتتبع — 4 جداول
customer_shipment

الشحنة الفعلية

يحفظ: الشركة والمرسل/المستلم والأصل/الوجهة وحالة الشحنة والوزن القابل للفوترة.

العلاقة: لها parcels وفاتورة؛ وقد تعود إلى shipment_request.

parcel

طرد مفرد

يحفظ: tracking_number فريد عالمياً، الأبعاد والأوزان والحالة والموقع الحالي.

parcel_movement

proof_of_delivery

إثبات التسليم

يحفظ: اسم المستلم، OTP، توقيع/صور وموقع التسليم وطريقة الاستلام.

vehicle_assignment

trip

رحلة نقل

يحفظ: السائق والمركبة والأصل والوجهة وحالة ومواعيد الرحلة.

manifest_item

سطر طرد داخل البيان

يحفظ: manifest_id وparcel_id وحالة التحميل/التفريغ.

قيد مهم: لا يمكن إدراج نفس الطرد مرتين في البيان نفسه.

06 — ORM بدون لخبطة

Prisma مقابل TypeORM، وأين يأتي Kysely؟

الواقع في مشروعك: schema.prisma هو مصدر تعريف نموذج البيانات. Prisma ينفذ عمليات الكتابة، وKysely يقرأ ويبني joins/filters المعقدة. TypeORM ليس جزءاً من هذا المشروع.
النقطة Prisma TypeORM Kysely في مشروعك
ما هو؟ ORM مع schema declarative وClient مولّد ومigrations. ORM تقليدي TypeScript/JavaScript. Type-safe SQL query builder، وليس ORM كاملاً.
تعريف البيانات schema.prisma مستقل عن classes. غالباً TypeScript classes مع decorators مثل @Entity(). يستهلك types مولّدة من schema Prisma هنا.
الوصول للبيانات prisma.parcel.create() ويرجع plain objects. Repository / Entity Manager / QueryBuilder، وقد يدعم Active Record أو Data Mapper. selectFrom(...).innerJoin(...) لبناء SQL واضح.
أفضل استخدام هنا Command side: create/update/delete وtransactions. غير مستخدم هنا؛ خيار بديل لو اختير في البداية. Query side: قوائم، filters، joins، pagination، read models.
migrations Prisma Migrate يولّد ويحفظ SQL في prisma/migrations. migrations خاصة بـ TypeORM CLI/files. لا يدير migrations وحده.

لماذا Prisma للكتابة؟

  • Client مولّد ومتحقق من أنواع schema.
  • CRUD وnested writes مريحان.
  • يتكامل مع transaction service في المشروع.
  • الـ migrations موجودة ومؤرشفة مع الكود.

لماذا Kysely للقراءة؟

  • الاستعلامات المعقدة ذات joins كثيرة تكون صريحة وسهلة التحكم.
  • يعطي TypeScript types بدون تحويل كل شيء إلى entities.
  • يناسب CQRS الخفيف هنا: read وwrite لهما احتياجات مختلفة.
  • لا يعني وجود قاعدتي بيانات أو نسختين من البيانات.

ما المقصود بـ CQRS هنا؟

ليس Microservices ولا Event Sourcing بالضرورة. هو فصل مسؤولية Commands (تغير الحالة) عن Queries (تقرأ وتعرض البيانات). عندك غالباً ملفات *.command.repository.ts تستخدم Prisma وملفات *.query.repository.ts تستخدم Kysely.

Command: HTTP → Command Service → Prisma → PostgreSQL Query: HTTP → Query Service → Kysely → PostgreSQL

هذه قاعدة الغالب في الموديولات الغنية، وليست قانوناً مطلقاً: مثلاً موديول auth يستخدم Prisma مباشرة لبعض القراءات والكتابات البسيطة.

معلومة المقارنة العامة مستندة إلى وثائق Prisma ORM وشرح TypeORM لأنماط Active Record/Data Mapper.

07 — تدفقات قد يسألون عنها

أهم قواعد العمل والتفاصيل الذكية

1. كيف يُحسب السعر؟

يعثر النظام أولاً على وحدات الشركة القادرة على خدمة origin وdestination، ثم يأخذ zone_pricing_matrix و tenant_pricing_settings.

volumetricWeight = (length × width × height) / divisor chargeableWeight = max(actualWeight, volumetricWeight) additionalWeight = max(0, chargeableWeight - baseWeight) total = basePrice + additionalWeight × pricePerExtraKg + extraFees

إن لم توجد إعدادات حجمية سليمة، ينشئ العرض كـ manual pricing بدلاً من سعر خاطئ.

2. لماذا transaction قصيرة؟

عند إنشاء شحنة، الكود يفعل العمل البطيء (توليد label/PDF وحفظه) قبل فتح المعاملة. بعدها فقط يكتب الشحنة والطرود والفاتورة وتحويل الطلب داخل transaction.

الهدف: لا تبقى قاعدة البيانات مقفلة بينما ننتظر ملفاً أو خدمة خارجية، لكن البيانات الجوهرية إما تنجح معاً أو تفشل معاً.

3. لماذا يوجد version؟

على shipment وparcel وinvoice يوجد version لـ optimistic locking. التحديث يطلب نفس version الذي قُرئ؛ إن سبقته عملية أخرى، يفشل update بدلاً من أن يمسح التغيير الجديد بصمت.

النتيجة: رسالة Conflict وطلب retry، بدلاً من Lost Update.

4. كيف تُرقم الفواتير بأمان؟

invoice_counter عدّاد لكل شركة ولكل سنة. يتم increment atomically ضمن transaction التي تنشئ الفاتورة؛ بذلك لا يأخذ طلبان الرقم نفسه.

الشكل مثل: DAM-INV-2026-00001.

5. كيف يعمل التتبع؟

الحالة الحالية في parcel.current_status مفيدة للعرض السريع، أما التاريخ الكامل فهو في parcel_movement. عند تغيير الحالة يسجل النظام السابق والجديد والمنفذ والموقع والرحلة.

6. ماذا يحدث عند التسليم؟

لا يكفي تغيير status فقط: ينشئ Proof of Delivery، وينقل الطرد إلى COLLECTED عند الحاجة، ويسجل tracking event ويعيد حساب حالة الشحنة. إن كان الدفع على المستلم فقد يسجل payment في نفس transaction.

أمثلة على حالات مسموحة/غير مسموحة

الحالة قاعدة العمل أين تُحمى؟
إلغاء شحنة يسمح قبل dispatch فقط، ويُلغي الفاتورة إن لم يُسجَّل قبضها. Domain entity + command service + billing facade.
إثبات تسليم مرة واحدة فقط للطرد، ولا يكون الطرد قبل READY_FOR_COLLECTION. unique DB constraint + entity assertion + service.
تغيير حالة طرد يجب أن يكون transition قانونياً؛ ثم يسجل movement ويعيد حساب shipment. Parcel entity + transaction + optimistic lock.
إنشاء فاتورة هي جزء من إنشاء الشحنة، لا endpoint CRUD حرّ. CustomerShipment → BillingFacade ضمن transaction.

خدمات البنية التي لا تنساها

Redis Cache-Aside

decorators مثل @Cacheable تقرأ cache ثم database عند miss، و@CacheEvict تحذف المفتاح بعد تغيير البيانات.

PostGIS وGiST

locations في العناوين والمواقع والفروع تستخدم geometry؛ GiST index يساعد في استعلامات المكان لاحقاً.

تخزَّن FCM tokens في user_device_token، وFirebase module يرسل الإشعارات أو يتعامل مع topics.

Job يومي للفواتير

ملاحظات تحقق قبل الديمو — فحص static للكود، وليست ميزات تدّعي أنها مكتملة

هذه نقاط مفيدة إذا سألك المشرف: “ماذا راجعت؟” لا تقل إنها مشاكل مؤكدة في runtime من دون test، بل قل إنك وجدتها في المراجعة وتحتاج integration test أو إصلاحاً قبل الإنتاج.

  • Bruno يضع base URL على /api/v1، لكن main.ts لا يضع setGlobalPrefix("api") ولا يظهر @Version() على الـ controllers؛ تحقق من URL الحقيقي قبل العرض.
  • Dockerfile يشغّل docker-entrypoint.sh ويعمل chmod لمساره، لكن لا يوجد فيه COPY واضح للسكريبت إلى /usr/local/bin؛ production image يحتاج build test.
  • في تحديث parcel/POD، repository الخاص بالـ tracking يحقن PrismaService مباشرة، بينما كتابة parcel تستخدم TransactionalPrismaService. كما أن بعض reads داخل transaction تتم من Kysely pool مستقل. هذا يعرّض وعد “كل شيء atomic/read-your-writes” للخطر ويستحق اختباراً تكاملياً.
  • مولد quotation اليدوي ينتج WAITING_PRICING_REQUEST، لكن QuotationCommandRepository.createMany يحفظ كل العروض كـ PENDING ولا يحفظ بعض حقول العرض اليدوي؛ المسار اليدوي يستحق اختباراً وإصلاحاً.
  • scope العميل للـ quotations فارغ في ShipmentRequestVisibilityScope، وقراءة quotation مباشرة بالـ id لا تتحقق من ملكية الطلب الأب؛ اختبر authorization لهذا المسار قبل الإنتاج.

09 — قسم المقابلة / التسليم

أسئلة ممكن تنسأل، مع جواب مختصر تحفظ فكرته

لا تحفظ النص حرفياً. افهم الجواب ثم قلّه بطريقتك. إن لم تكن متأكداً من نقطة تنفيذية، قل “بحسب الكود الحالي…” وهذا جواب مهني وصادق.

1. اشرح المشروع خلال 30 ثانية.

هو backend لمنصة شحن SaaS متعددة الشركات. كل شركة tenant معزولة منطقياً ببياناتها. يغطي دورة الشحنة كاملة: طلب، تسعير، عرض، شحنة وطرود، نقل، تتبع، إثبات تسليم، فاتورة ودفع. بنيته NestJS modular monolith مع PostgreSQL وPrisma/Kysely.

2. ما معنى Multi-Tenant هنا؟

عدة شركات تستخدم نفس التطبيق ونفس schema، لكن كل سجل تشغيلي تقريباً يحمل tenant_id. الـ Principal والسياسات وقيود query تمنع تسرب بيانات شركة إلى أخرى.

3. ما الفرق بين tenant وuser وcustomer_profile؟

tenant هو الشركة، users هو حساب الدخول العام، وcustomer_profile هو معلومات العميل التجارية المرتبطة بحساب واحد. الموظف أيضاً قد يرتبط بحساب users لكن يمثل علاقة الموظف بالشركة.

4. هل تستخدمون TypeORM؟ وما الفرق عن Prisma؟

لا، المشروع يستخدم Prisma وKysely. Prisma يعتمد schema.prisma ويولّد typed client وmigrations؛ TypeORM يعتمد غالباً entities مع decorators وrepositories. اخترنا Prisma للـ writes وKysely للـ read queries المعقدة.

5. لماذا تجمعون Prisma وKysely؟ أليس هذا تكراراً؟

ليس تكراراً للبيانات. Prisma مناسب للـ command side والمعاملات والكتابة، وKysely يتيح SQL-like typed queries لجلب read models ذات joins وفلاتر كثيرة. الاثنان على نفس PostgreSQL ونفس schema/types.

6. ما الفرق بين shipment request وquotation وshipment؟

request هو طلب العميل قبل التنفيذ، quotation هو عرض سعر ممكن أن يكون واحداً من عدة عروض، وshipment هو السجل التشغيلي الفعلي لدى الشركة بعد القبول وتحويل الطلب.

7. كيف يمنع النظام lost updates عندما يغير اثنان حالة طرد؟

يستخدم optimistic locking. يقرأ version ثم ينفذ update حيث id وversion متطابقان ويزيد version. إن كانت count = 0 فهذا يعني أن عملية أخرى سبقتنا، فنرجع Conflict بدلاً من overwrite صامت.

8. ما الذي يدخل في transaction عند إنشاء شحنة؟ ولماذا؟

إنشاء shipment والـ parcels والفاتورة وتحويل shipment request. هذه حقائق أعمال يجب أن تنجح معاً أو تفشل معاً. أما توليد PDF/label ورفعه فخارج transaction لأنه I/O بطيء لا يجب أن يطيل القفل.

9. كيف يُحسب الوزن القابل للدفع؟

نأخذ max بين الوزن الفعلي والوزن الحجمي. الوزن الحجمي = الطول×العرض×الارتفاع ÷ divisor الخاص بالشركة؛ ثم تضاف كلفة الوزن الزائد فوق base weight إلى base price والرسوم الإضافية.

10. لماذا تحتاج global_location وorganization_unit معاً؟

global_location هو قاموس جغرافي عام مشترك (مدينة، محافظة، منطقة). organization_unit هو فرع/مستودع تابع لشركة. جدول mapping يقول أي وحدات تغطي أي مواقع، وهذا مهم لاختيار مسار خدمة الطلب.

11. كيف يمثل النظام صلاحيات الموظف داخل فرع معين؟

employee مرتبط بـ employee_assignment إلى organization_unit، ثم assignment_role يربط التعيين بالـ role. وهكذا قد يملك الشخص دوراً مختلفاً حسب الفرع. role_permission يحدد الصلاحيات النهائية.

12. كيف يتم التتبع؟ ولماذا لا يكفي current_status؟

current_status يعطي الحالة الحالية بسرعة، لكن parcel_movement يعطي timeline قابل للتدقيق: من غيّر ماذا، متى، أين، وأي رحلة مرتبطة به. لذلك نحتاج الاثنين.

13. ما هو Proof of Delivery؟ وما الضمانات عليه؟

هو دليل أن الطرد سُلّم: مستلم، OTP وتوقيع/صور وموقع عند الحاجة. قاعدة البيانات تفرض uniqueness على parcel_id، والخدمة تمنع تسجيله قبل أن يصبح الطرد قابلاً للاستلام.

14. لماذا invoice_counter موجود منفصلاً؟

للحصول على رقم فاتورة متسلسل لكل شركة وكل سنة بأمان عند تزامن الطلبات. يتم atomic upsert في نفس transaction مع إنشاء الفاتورة.

15. ما فائدة Redis في المشروع؟

يستخدم Cache-Aside: القراءة من Redis أولاً، ثم database عند عدم وجود القيمة. بعد التعديل تُزال المفاتيح المناسبة حتى لا تعرض الواجهة بيانات قديمة.

16. كيف تحمي API من بيانات غير صالحة؟

DTOs مع class-validator وValidationPipe مفعّل globally مع whitelist وtransform؛ الحقول غير المسموحة تُزال والتحويلات الأساسية تحدث قبل دخول الخدمة. الأخطاء تُنسق عبر GlobalExceptionFilter.

17. لماذا Request Context وAsyncLocalStorage؟

حتى يتاح Principal وrequestId/correlationId في كامل سلسلة الطلب من دون تمرير request يدوياً بين كل services وrepositories، مع بقاء كل request معزولاً عن concurrent requests.

18. كيف تعمل جلسة refresh token؟

refresh token لا يخزن plain text؛ يخزن hash في user_session. عند refresh يتحقق bcrypt ثم يحذف الجلسة القديمة وينشئ tokens وجلسة جديدين (rotation). التوكن المزيف/القديم قد يسبب حذف الجلسة لأمان أكبر.

19. هل هذا Microservices أو Monolith؟

هو Modular Monolith: deploy واحد وprocess واحد وقاعدة واحدة، لكن موديولات أعمال واضحة مثل tenant وfleet وbilling. هذا أقل تعقيداً من microservices مع الحفاظ على حدود داخلية عبر facades.

20. ما الموجود في mobile وfrontend حالياً؟

mobile هو Flutter وفيه login/register/OTP وشاشات شركات وإنشاء طرد، مع Riverpod وGoRouter. بحسب الكود الحالي لا يوجد HTTP client يربطه بالـ backend بعد. frontend يحتوي README فقط، لذلك لا أدّعي وجود Web frontend مكتمل.

21. ما الاختبارات الموجودة؟

في backend توجد Jest unit specs للـ services/repositories/domain entities، وe2e specs تحت test، إضافة إلى Bruno collections لتجربة endpoints. الجواب الأقوى: نركز الاختبارات على business rules والعمليات الحرجة مثل transaction والحالات والتزامن.

22. ما الشيء الذي ستطوره لاحقاً لو أعطوك وقتاً؟

أربط Flutter بالـ API مع طبقة networking/auth/secure token storage، أو أوحّد مساري employee وemployee2 بعد تحديد المعتمد، أو أضيف observability ومراقبة cache والأخطاء. لا تقل “سأعيد كتابة كل شيء”؛ اقترح تحسيناً محدداً ومبرراً.

فخّان شائعان في الإجابة: لا تسمّي Kysely ORM، ولا تقل إن CQRS يعني أن لديك microservices أو قاعدتي بيانات. ولا تخترع أن واجهة الويب مكتملة بينما مجلد frontend لا يحتوي إلا README.

خريطة الدليل إلى الكود

كل الكلام المتعلق بالمشروع مأخوذ من الملفات التالية في النسخة الحالية، لا من افتراضات عامة:

  • backend/prisma/schema.prisma — الـ 45 model والـ 31 enum والعلاقات والقيود والفهارس.
  • backend/package.json وbackend/README.md — التقنيات وscripts وفصل Prisma/Kysely.
  • backend/src/main.ts وbackend/src/app.module.ts — تشغيل API والحماية والموديولات.
  • backend/src/infrastructure/database/prisma.service.ts وdatabase.module.ts — دمج Prisma وKysely.
  • backend/src/modules/* — الخدمات والـ controllers وقواعد الشحن والفوترة والأسطول.
  • backend/src/packages/context وauthorization وtransaction — request context والصلاحيات والمعاملات.
  • mobile/lib وmobile/pubspec.yaml — واجهة Flutter وحالتها الحالية.
  • docker-compose.yml وnginx/ — PostgreSQL/PostGIS وRedis وreverse proxy.
مصدر الحقيقة للـ database: اعتمد schema.prisma وprisma/migrations. ملف backend/prisma/DDL.sql أقدم وغير مطابق للحالة الحالية (يعرض عدداً وحالات قديمة)، لذلك لا تحفظه ولا تشغّله فوق migrations.

للمفاهيم العامة فقط: راجع Prisma ORM official documentation وTypeORM official guide.

أُنشئ هذا الدليل للدراسة من كود المشروع الحالي. افتحه في المتصفح، أو استخدم طباعة المتصفح إلى PDF للمراجعة السريعة.
