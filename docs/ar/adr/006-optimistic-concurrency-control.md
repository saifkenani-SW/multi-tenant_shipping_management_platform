# ADR-006: التحكم المتفائل بالتزامن (OCC) للكيانات اللوجستية

## الحالة (Status)
مقبول (Accepted)

## السياق (Context)
في البيئات اللوجستية سريعة الحركة، تمر الشحنات والطرود بتغييرات حالة متتالية يقودها أطراف متعددون في نفس التوقيت: عمال المستودعات الذين يمسحون الباركود عند بوابات الفرز، منسقو الرحلات الذين يحملون الشاحنات، السائقون على الطرقات، وعمليات إعادة الحساب الآلية للحالات.
عندما تحاول عمليتان متزامنتان قراءة وتعديل نفس السجل، فإن التحديثات التقليدية قد تؤدي إلى مسح أحد التعديلين بالكتابة فوقه دون قصد، وهي المشكلة المعروفة بـ (Lost Update Problem).

## القرار (Decision)
قمنا بتطبيق **التحكم المتفائل بالتزامن (Optimistic Concurrency Control - OCC)** بالاعتماد على عمود رقمي `version` في الكيانات اللوجستية عالية التردد (`customer_shipment` و `parcel`).
تُنفذ طفرات الحالة من خلال تحديثات شرطية ذرية:
```typescript
const result = await this.prisma.client.customer_shipment.updateMany({
  where: { id: shipmentId, version: currentVersion },
  data: { status: newStatus, version: { increment: 1 } },
});

if (result.count === 0) {
  throw new ConflictException(
    'Shipment was modified by another process. Please retry.',
  );
}
```

## المبررات (Why)
1. **تجنب قفل صفوف قاعدة البيانات (No Row Locking)**: القفل المتشائم (`SELECT FOR UPDATE`) يحتجز أقفال الصفوف عبر حدود المعاملة، مما يسبب بطئاً شديداً ومخاطر حقيقية لحدوث تعليق دائم (Deadlocks) تحت الضغط العالي لمسح الباركود.
2. **معالجة حتمية للتعارض**: عند حدوث تضارب في الإصدار، تفشل العملية فوراً عبر استثناء تعارض صريح `ConflictException`، مما يمكن العميل أو الخدمة المستدعية من إعادة تحميل الحالة الأحدث والمحاولة بأمان.
3. **التوافق التام مع قواعد البيانات**: لا تتطلب زيادة رقم الإصدار أي ميزات خاصة من قاعدة البيانات، وتعمل بكفاءة واتساق تام عبر Prisma و PostgreSQL.

## البدائل التي تمت دراستها (Alternatives Considered)
- **القفل المتشائم (Pessimistic Locking / `SELECT FOR UPDATE`)**: رُفض لأن حجز السجلات أثناء انتظار عمليات التحقق أو عمليات الإدخال/الإخراج الخارجية يقلل من معدل معالجة الطلبات ويزيد من احتمالات الـ Deadlocks.
- **استراتيجية الفوز لآخر كاتب (Last-Write-Wins بدون إصدارات)**: رُفضت لأنها تتسبب في فقدان التحديثات الحرجة (مثل مسح قديم وصل متأخراً يكتب حالة `IN_TRANSIT` فوق شحنة تم تسليمها بالفعل `DELIVERED`).

## التبعات والنتائج (Consequences)
### الإيجابية (Positive)
- إنتاجية قراءة وكتابة مرتفعة دون احتجاز أقفال قاعدة البيانات لفترات طويلة.
- ضمان سلامة انتقالات الحالة ومنع الكتابة فوق التعديلات المتزامنة.
- تطبيق الحماية مباشرة عند حدود استدامة المستودع.

### السلبية (Negative)
- يجب على المستدعين والخدمات معالجة استثناء `ConflictException` وتطبيق سياسات إعادة المحاولة (Retry Policies) عند الحاجة.
