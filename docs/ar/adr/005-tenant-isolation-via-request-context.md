# ADR-005: عزل المستأجرين عبر سياق الطلب و AsyncLocalStorage

## الحالة (Status)
مقبول (Accepted)

## السياق (Context)
في تطبيقات SaaS متعددة المستأجرين التي تشترك في قاعدة بيانات واحدة، يُعد منع وصول مستأجر لبيانات مستأجر آخر مطلباً أساسياً وأولوية أمنية قصوى.
إن الاعتماد على استخراج `tenantId` يدوياً من ترويسات HTTP أو حمولات الطلبات داخل المتحكمات ثم تمريره عبر طبقات الخدمات هو أسلوب عرضة للأخطاء البشرية؛ إذ إن نسيان شرط تصفية واحد في أي استعلام قد يكشف بيانات الشحن الحساسة لمستأجر آخر.

## القرار (Decision)
قمنا بتطبيق سياق تشغيلي مقيد بدورة حياة الطلب باستخدام ميزة Node.js **`AsyncLocalStorage`** داخل الحزمة `src/packages/context`.
يقوم وسيط `ContextMiddleware` باعتراض كل طلب وارد، وربط كائن الهوية النشط `Principal` (الذي يحمل الـ `tenantId` المعتمد)، وإتاحة هذا السياق برمجياً في أي نقطة عبر الخدمات وبناة الرؤية طوال فترة معالجة ذلك الطلب.

## المبررات (Why)
1. **العزل التلقائي (Implicit Scoping)**: تحصل خدمات التطبيق وبناة الاستعلام على معرف المستأجر النشط بشكل آمن وموثوق عبر `RequestContextService.getTenantIdOrThrow()`، مما يقضي على مخاطر التلاعب بالمعاملات من جانب العميل.
2. **فك الارتباط عن إطار العمل**: يصل منطق النطاق وبناة الرؤية إلى السياق الأمني دون الحاجة للاعتماد المباشر على كائن `Request` الخاص بـ Express.
3. **البيانات الوصفية المشتركة**: تمرير تلقائي لمعرف الطلب `requestId` ومعرف الارتباط `correlationId` وتتبع OpenTelemetry دون الحاجة لتمرير معاملات إضافية في كل دالة.

## البدائل التي تمت دراستها (Alternatives Considered)
- **قاعدة بيانات منفصلة لكل مستأجر (Database Per Tenant)**: رُفضت بسبب التكاليف التشغيلية الباهظة، واستنزاف اتصالات قاعدة البيانات، وصعوبة إدارة وتطبيق ترحيلات المخطط لمئات المستأجرين.
- **مخطط منفصل لكل مستأجر (Schema Per Tenant)**: رُفضت لأن تنفيذ ترحيلات DDL في PostgreSQL عبر مئات المخططات الديناميكية يتسبب في بطء شديد وتجزئة مسبح الاتصالات.
- **مزودات NestJS المقيدة بنطاق الطلب (`Scope.REQUEST`)**: رُفضت لأن مزودات `Scope.REQUEST` تعيد بناء شجرة حقن التبعيات (DI Tree) مع كل طلب HTTP، مما يدهور أداء الخادم واستجابته تحت الضغط العالي.

## التبعات والنتائج (Consequences)
### الإيجابية (Positive)
- أداء فائق: بقاء خدمات NestJS كمزودات فردية وحيدة (Singletons) مع التمتع بسياق خاص بكل طلب.
- هوية أمنية موحدة وموثوقة (`Principal`).
- تمكين التصفية التلقائية عبر بناة مجالات الرؤية (Visibility Scope Builders).

### السلبية (Negative)
- التدفقات غير المتزامنة المنفصلة (مثل معالجات الأحداث أو المهام المجدولة Cron) تعمل خارج دورة حياة طلبات HTTP ولا ترث سياق ALS تلقائياً. يجب على المهام الخلفية التعامل مع حدود المستأجر صراحة.

## التطبيق البرمجي (Implementation)
- `src/packages/context/context.module.ts`: تسجيل الموديول العام.
- `src/packages/context/middlewares/context.middleware.ts`: تهيئة مخزن ALS لكل طلب.
- `src/packages/context/services/request-context.service.ts`: واجهة برمجة الوصول للسياق.
