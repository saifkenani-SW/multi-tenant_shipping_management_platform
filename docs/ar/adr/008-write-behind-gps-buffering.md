# ADR-008: التخزين المؤقت للإحداثيات بنمط Write-Behind في Redis

## الحالة (Status)
مقبول (Accepted)

## السياق (Context)
أثناء سير رحلات التوصيل، ترسل أجهزة السائقين المحمولة إحداثيات الـ GPS المباشرة إلى الخادم عبر WebSockets كل 3 ثوانٍ تقريباً.
في بيئة أسطول يضم عشرات أو مئات السائقين النشطين، فإن كتابة كل نبضة إحداثيات منفردة بشكل متزامن في PostgreSQL يُحدث تضخيماً هائلاً في عمليات الكتابة (Write Amplification)، وتحديثات مستمرة ومكلفة لفهارس PostGIS المكانية، ويؤدي سريعاً إلى استنزاف مسبح اتصالات قاعدة البيانات.

## القرار (Decision)
قمنا بتطبيق **نمط التخزين المؤقت المرحل (Write-Behind Caching Pattern)** بالاعتماد على قوائم Redis الخفيفة وتفريغ مجدول بدفعات:
1. عند وصول الإحداثيات إلى بوابة `TrackingGateway`، يتم بثها فورياً لمشتركي غرفة الـ WebSocket النشطة للرحلة (`trip:{tripId}`).
2. في نفس الوقت، تُلحق الإحداثيات (`RPUSH`) في قائمة Redis خفيفة بالذاكرة: `trip:locations:{tripId}`.
3. تقوم خدمة مجدولة (`LocationFlusherService`) كل دقيقتين بسحب الإحداثيات المتجمعة ذرياً من Redis عبر معاملة `MULTI` / `EXEC` (`LRANGE` + `LTRIM`)، ثم إدراجها بدفعة واحدة (Bulk Insert) في جدول `trip_location_log` داخل PostgreSQL باستخدام استعلام `createMany` فردي.

```text
تطبيق السائق ──(WS: كل 3ث)──► TrackingGateway ──► بث مباشر لعملاء الويب والهاتف
                                    │
                                    └──► مخزن Redis المؤقت (RPUSH trip:locations:{tripId})
                                                  │
                                                  ▼ (مجدول Cron: كل دقيقتين)
                                         LocationFlusherService
                                                  │
                                                  └──► إدراج جماعي Bulk INSERT في PostgreSQL
```

## المبررات (Why)
1. **زمن استجابة فائق في الاستيعاب (Sub-millisecond Latency)**: تستغرق الكتابة في قوائم Redis بالذاكرة أجزاءً ضئيلة من المللي ثانية، مما يبقي حلقة أحداث WebSockets سريعة وخفيفة دون أي حظر.
2. **حماية خادم قاعدة البيانات**: دمج آلاف الإدراجات الفردية المتفرقة في استعلام تجميعي واحد دوري، مما يقلل بشكل جذري من تكلفة المعاملات وضغط الإدخال/الإخراج (Disk I/O) على PostgreSQL.
3. **التفريغ الذري الآمن**: يضمن استخدام `MULTI/EXEC` مع `lrange` و `ltrim(key, 1, 0)` عدم فقدان أي إحداثيات يرسلها السائقون أثناء لحظة تنفيذ عملية التفريغ الدوري.

## البدائل التي تمت دراستها (Alternatives Considered)
- **الكتابة المباشرة المتزامنة في PostgreSQL**: رُفضت لأن آلاف عمليات الإدراج الفردية في الدقيقة تفقد قاعدة البيانات كفاءتها وتستنزف اتصالات المسبح.
- **استخدام وسيط رسائل مخصص (Kafka أو RabbitMQ)**: رُفض لأن إضافة عنقود خوادم لتدفق الرسائل يفرض تعقيداً تشغيلياً وتكاليف بنية تحتية مفرطة لا يحتاجها المشروع في مرحلته الحالية، بينما خادم Redis موجود بالفعل ومستخدم كذاكرة مؤقتة.

## التبعات والنتائج (Consequences)
### الإيجابية (Positive)
- منع استنزاف اتصالات قاعدة البيانات تحت ضغط تليماتكس الأسطول.
- الاحتفاظ بتحديثات الخرائط اللحظية الفورية للعملاء عبر WebSockets.
- سحب آمن وذري لبيانات التتبع دون أي فقدان.

### السلبية (Negative)
- تأخر ظهور إحداثيات الـ GPS في التقارير التاريخية المستعلمة من SQL لمدة قد تصل إلى دقيقتين كحد أقصى.
- في حال إعادة تشغيل خادم Redis بشكل مفاجئ دون تفعيل آليات الاستدامة (AOF أو RDB)، قد تُفقد الإحداثيات المحتجزة في نافذة الدقيقتين الجاريتين.
