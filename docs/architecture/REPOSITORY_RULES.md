# Repository Architecture Rules

These rules are mandatory for every Repository in this project.

Do not deviate from them unless explicitly instructed.

===============================================================================
ARCHITECTURAL ROLE
===============================================================================

Repositories are the persistence boundary.

Their responsibility is to translate between the persistence layer and the application's Entities.

Repositories are responsible for:

- Loading Entities.
- Persisting data.
- Updating data.
- Deleting data.
- Executing database queries.

Repositories are NOT responsible for:

- Business rules.
- Business workflows.
- Validation.
- Authorization.
- HTTP concerns.
- DTO mapping.
- Transaction management.
- Cache invalidation.
- Calling other repositories.

Business orchestration always belongs to the Application Service.

===============================================================================
PERSISTENCE TECHNOLOGY
===============================================================================

This architecture is fixed.

Commands use Prisma.

Queries use Kysely.

Do not replace them.

Do not introduce ORM abstractions.

Do not design for hypothetical future ORMs.

===============================================================================
COMMAND / QUERY SEPARATION
===============================================================================

Command Repositories use Prisma.

Query Repositories use Kysely.

Regardless of the persistence technology, Repository contracts must remain identical.

The Application layer must never know whether Prisma or Kysely is being used.

===============================================================================
ENTITY CONTRACT
===============================================================================

Repositories always return Application Entities.

Never return:

- Prisma models
- Kysely rows
- Database records
- DTOs
- any

Good:

Tenant
User
Role
Permission
SubscriptionPlan

Bad:

TenantDto
TenantData
PrismaTenant
Selectable<DB['tenant']>

Entities are the only contract shared between the Repository and the Application layer.

===============================================================================
ENTITIES
===============================================================================

Entities represent business data.

Some Entities currently contain only state.

Some Entities may later contain business behavior.

Both are acceptable.

Do NOT introduce duplicate models such as:

TenantData
RoleData
SubscriptionPlanData

There should be only one Entity representing the concept.

===============================================================================
ENTITY CONSTRUCTION
===============================================================================

Repositories are responsible for constructing Entities.

Application Services must never construct Entities from persistence models.

Persistence models must never leave the Repository layer.

Flow:

Database

↓

Repository

↓

Entity

↓

Application Service

===============================================================================
MAPPING
===============================================================================

Repositories perform explicit mapping between persistence models and Entities.

Never expose ORM models outside the Repository.

Avoid:

- object spreading
- implicit mapping
- leaking persistence models

Bad:

return {
    ...row
}

Good:

return new Tenant(
    row.id,
    row.name,
    row.status,
    ...
)

===============================================================================
FILTERING
===============================================================================

Repositories receive business filters.

Example:

TenantFilter

Repositories internally translate them into:

- Prisma WhereInput
- Kysely queries

Database query objects must never leave the Repository.

===============================================================================
IDENTITY
===============================================================================

Repositories never generate entity identifiers.

Identifiers are generated by Prisma using schema defaults.

Repositories simply return the resulting Entity.

Do not generate UUIDs inside repositories unless explicitly required by the business.

===============================================================================
TRANSACTIONS
===============================================================================

Repositories are completely unaware of transactions.

Repositories must never:

- call prisma.$transaction()
- receive TransactionClient
- receive tx parameters
- read AsyncLocalStorage
- resolve transaction context

Repositories always use:

this.prisma.client

The transaction infrastructure automatically decides whether the current client is:

- PrismaService
- TransactionClient

Repositories never care.

===============================================================================
CACHING
===============================================================================

Repositories contain no caching logic.

Read operations may be decorated externally.

Repositories never invalidate cache.

Cache invalidation belongs to the Application Service because it is part of the business workflow.

===============================================================================
ERROR HANDLING
===============================================================================

Repositories translate only persistence errors that have business meaning.

Examples:

- Unique constraint violations
- Record not found
- Foreign key violations (when appropriate)

Unexpected infrastructure failures must propagate to the global exception handler.

Repositories must never swallow unexpected exceptions.

===============================================================================
DEPENDENCIES
===============================================================================

Repositories must never depend on other repositories.

Repositories communicate only with the persistence layer.

Repository orchestration belongs to the Application Service.

===============================================================================
METHOD DESIGN
===============================================================================

Repository methods represent business persistence operations.

Examples:

findById()

findByEmail()

findByCode()

findMany()

exists()

count()

create()

update()

delete()

activate()

deactivate()

Avoid exposing generic persistence APIs simply because Prisma supports them.

Every Repository method should exist because an Application use case requires it.

===============================================================================
TYPE SAFETY
===============================================================================

No any.

Repositories must be fully type-safe.

Use explicit types everywhere.

===============================================================================
CONSISTENCY
===============================================================================

Every Repository in every module must follow exactly the same architecture.

Do not introduce alternative Repository styles.

Do not mix Repository patterns.

Architectural consistency is more important than personal coding preferences.

When in doubt, prefer consistency over cleverness.
