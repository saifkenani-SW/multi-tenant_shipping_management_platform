# Database Rules

## Purpose

This document defines the persistence architecture and database access rules of the Multi-Tenant Shipping Management Platform.

The database layer is an implementation detail.

Business correctness always has higher priority than persistence convenience.

---

# 1. Persistence Philosophy

The project separates:

Business Model

↓

Persistence Model

Business logic must never depend on the persistence implementation.

---

# 2. CQRS Strategy

The project adopts a lightweight CQRS approach.

Writes use:

- Prisma ORM

Reads use:

- Kysely

This separation improves:

- Performance
- Readability
- Query flexibility
- Reporting
- Complex joins

The project does NOT implement Event Sourcing.

---

# 3. Write Side

All write operations use Prisma.

Examples:

Create

Update

Delete

Transactions

Aggregate persistence

Relation updates

Never perform writes using Kysely.

---

# 4. Read Side

All read operations use Kysely.

Examples:

Search

Filtering

Sorting

Reporting

Dashboard queries

Tracking

Pagination

Complex joins

Read projections

Never use Prisma for complex read models.

---

# 5. Repository Responsibilities

Repositories exist only for write operations.

Repositories belong to Aggregate Roots.

Repositories encapsulate Prisma.

The Domain never depends on Prisma.

---

# 6. Query Services

Read operations use Query Services.

Query Services encapsulate Kysely.

Query Services never return Domain Aggregates.

They return Read Models only.

---

# 7. Domain Layer

The Domain Layer never imports:

Prisma

Kysely

SQL

Database Models

ORM Types

The Domain remains persistence independent.

---

# 8. Application Layer

Application Services orchestrate:

Repositories

Query Services

Transactions

Domain Events

The Application Layer decides whether a request is:

Command

or

Query

---

# 9. Transactions

Transactions belong exclusively to write operations.

Transactions use Prisma only.

Never execute Kysely queries inside Prisma transactions unless absolutely necessary.

Transactions should remain short.

---

# 10. Read Models

Read Models are optimized for reading.

They may contain:

Joined data

Computed values

Denormalized structures

Read Models are never persisted.

Read Models are never reused as Domain Entities.

---

# 11. Domain Entities

Domain Entities are optimized for business behavior.

Read Models are optimized for presentation.

Never confuse the two.

---

# 12. Mapping Rules

Infrastructure performs mapping.

Prisma

↓

Persistence Model

↓

Mapper

↓

Domain Model

For queries:

SQL

↓

Kysely

↓

Read Model

No Domain mapping is required unless business logic is executed.

---

# 13. Tenant Isolation

Every write operation must execute inside the authenticated tenant.

Every read operation must also execute inside the authenticated tenant.

Tenant filtering is mandatory.

Platform administration is the only exception.

---

# 14. Aggregate Loading

Repositories load only the Aggregate required for the current use case.

Avoid loading unnecessary relations.

Avoid eager loading large object graphs.

Aggregates define consistency boundaries, not navigation convenience.

---

# 15. Query Optimization

Kysely should be used for:

Multi-table joins

Reporting

Analytics

Dashboard statistics

Tracking pages

Search

Filtering

Sorting

Projection queries

Avoid Prisma include chains for complex read scenarios.

---

# 16. Pagination

All list queries must support pagination.

Never return unbounded collections.

Large datasets must use efficient pagination strategies.

---

# 17. Index Usage

Database indexes must support:

Tenant filtering

Tracking lookup

Foreign keys

Sorting

Frequent searches

Never optimize based on assumptions.

Optimize using measured bottlenecks.

---

# 18. UUID

All business entities use UUID identifiers.

UUIDs are generated by the application.

Database-generated sequential identifiers are prohibited.

Tracking Numbers are business identifiers.

They are not primary keys.

---

# 19. Soft Delete

Soft Delete is applied only where required by business rules.

Ledger tables are append-only.

Audit tables are append-only.

Never soft delete immutable business history.

---

# 20. Immutable Data

The following records are immutable:

Parcel Movement

Audit Log

Proof Of Delivery (after verification)

Paid Invoice (except refund workflow)

Immutable data must never be updated.

---

# 21. N+1 Queries

Avoid N+1 queries.

Prefer:

Single optimized Kysely query

Instead of:

Looping over repositories.

---

# 22. Database Migrations

Schema changes must be introduced through Prisma Migrations only.

Never modify production schema manually.

Migration history is part of the source code.

---

# 23. Raw SQL

Raw SQL is allowed only when:

Performance requires it

Kysely cannot express the query efficiently

Prisma cannot support the required feature

Every raw SQL query must be reviewed.

---

# 24. Forbidden Practices

Never:

Import Prisma into the Domain.

Import Kysely into the Domain.

Write SQL inside Controllers.

Write SQL inside Use Cases.

Use Prisma for reporting.

Use Kysely for writes.

Expose database models outside Infrastructure.

Return Prisma models to Controllers.

Return Kysely rows as Domain Entities.

Mix read and write responsibilities.

---

# 25. Architecture Summary

Write Flow

Controller

↓

Application Service

↓

Repository

↓

Prisma

↓

PostgreSQL

---

Read Flow

Controller

↓

Query Service

↓

Kysely

↓

PostgreSQL

---

# Final Principle

Prisma is the write model.

Kysely is the read model.

The Domain remains completely independent of both.

Persistence exists to support the Domain, never the opposite.
