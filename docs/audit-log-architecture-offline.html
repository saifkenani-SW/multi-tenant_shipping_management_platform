01

الخلاصة التنفيذية

القرار الذي أنصح أن نبدأ به الآن.

الاقتراح الأنسب للمشروع حالياً:
  1. إنشاء AuditModule مستقل يملك الجدول والـRepository ومنطق التنظيف والقراءة.
  2. الموديولات الأخرى تتعامل معه فقط عبر AuditFacade.record()، ولا تصل إلى Repository أو Prisma الخاص به.
  3. الـInterceptor يجمع معلومات HTTP فقط: IP، User-Agent، Request ID، Correlation ID، method وpath؛ لكنه لا يقرر الحدث التجاري.
  4. الـCommand Service الذي نفّذ العملية يحدد الحدث الحقيقي مثل ORGANIZATION_UNIT.CREATED ويرسل القيم القديمة والجديدة بعد تنقيحها.
  5. تسجيل العمليات الناجحة الحرجة يتم ضمن نفس @Transactional() حتى لا نحصل على سجل لعملية فشلت أو عملية نجحت بلا سجل.
  6. نبدأ بجدول واحد وفهارس مناسبة وCursor Pagination. لا نضيف Kafka ولا Partitioning ولا Outbox قبل وجود حاجة مقاسة.
الـInterceptor لوحده ليس Audit Business. هو يرى أن الطلب PATCH /... نجح، لكنه لا يعرف ماذا تغير فعلياً، ولا يعرف أحياناً معرّف الكيان الناتج، ولا يستطيع ضمان نفس Transaction.

فجوات مؤكدة

  • لا توجد فهارس مخصصة لاستعلامات Audit.
  • لا يوجد Listener لحدث الشحنة المكتشف.
  • EventEmitter2 داخل الذاكرة وغير دائم.
  • Request Context لا يلتقط IP وUser-Agent حالياً.
  • لا توجد سياسة Redaction أو Retention.
  • لا يوجد API قراءة وصلاحيات مخصصة.

أشياء مفيدة جاهزة

  • RequestContext يحوي request/correlation/principal.
  • يوجد TransactionalPrismaService يعيد استخدام Transaction الحالية.
  • المشروع يعمل بموديولات وFacades.
  • PostgreSQL وJSONB مناسبان لهذا الحجم كبداية.
  • UUID v7 مناسب للـCursor Pagination.
تعارض يجب تنظيفه: ملف الـmigration الفعلي يستخدم ON DELETE SET NULL لعلاقات المستخدم والـtenant، بينما ملف DDL.sql القديم يذكر CASCADE للـtenant. المرجع التنفيذي يجب أن يكون migrations/Prisma، ثم يتم تحديث DDL كي لا يضلل الفريق.
03

ما هو الـAudit وما الذي نسجله؟

الهدف هو إثبات من فعل ماذا ومتى وعلى أي كيان وبأي نتيجة.

Audit Log

سجل أعمال وأمان طويل العمر: تغيير صلاحية، إلغاء اشتراك، إنشاء فرع، تعديل حالة شحنة.

Application Log

تشخيص تقني: stack trace، latency، SQL error. غالباً يذهب إلى Pino/monitoring وليس جدول Audit.

Entity History

تاريخ كامل لكيان معين وقد يحتاج snapshot/versioning. قد يستخدم Audit لكن ليس دائماً نفس الحاجة.

نسجل هذه العمليات

  • تسجيل الدخول الناجح والفاشل، تغيير/استعادة كلمة السر.
  • إنشاء، تعديل، تعطيل أو حذف المستخدمين والموظفين.
  • تعديل الأدوار والصلاحيات والتعيينات.
  • تعديل إعدادات الـtenant والأسعار والاشتراك.
  • إنشاء/إلغاء الطلب وتغيير حالة الشحنة أو التسليم.
  • التصدير أو القراءة الحساسة على نطاق واسع.
  • لا نسجل كل GET عادي تلقائياً.
  • لا نسجل health checks أو Swagger assets.
  • لا نسجل body كامل لكل Request.
  • لا نسجل كلمات السر وOTP والتوكن والكوكيز.
  • لا نكرر logs التقنية داخل Audit.
  • لا نخزن ملفات مرفوعة أو Base64 داخل JSONB.

حل متوافق مع modular monolith وقاعدة التواصل عبر Facades.

حدود الربط: موديول الشحن أو الـtenant لا يحقن Audit Repository ولا Prisma Model. يتعامل فقط مع Facade بعقد بسيط يحتوي primitives وJSON منقحاً. الـAuditModule وحده يملك التخزين والفهارس وسياسة القراءة.

وبحسب قاعدة المشروع الخاصة بالـFacades: يوضع عقد الـFacade عند الموديول المستهلك، وينفّذ AuditModule هذا العقد. بهذه الطريقة لا يعرف موديول الشحن أو الـtenant أي تفاصيل داخلية عن Audit ولا يصبح هناك coupling بين الـrepositories أو الـentities.

تدفق عملية ناجحة وحرجة

الـMiddleware ينشئ Request Context ويجمع معلومات المصدر.
الـGuard يثبت principal وtenant من التوكن، لا من body.
Command Service يقرأ القديم وينفذ التعديل.
داخل نفس Transaction يستدعي AuditFacade.record().
ينجح التعديل والسجل معاً، أو يتراجعان معاً.

شكل عقد التسجيل المقترح

type AuditRecordInput = {
  eventType: 'ORGANIZATION_UNIT.CREATED' | 'ROLE.UPDATED' | string;
  entity: { type: string; id?: string };
  tenantId?: string;                  // يؤخذ من principal/السياق متى أمكن
  actor?: { type: 'USER' | 'SYSTEM' | 'API_KEY'; userId?: string };
  outcome: 'SUCCESS' | 'FAILURE' | 'DENIED';
  changes?: {
    before?: Record<string, unknown>;
    after?: Record<string, unknown>;
  };
  metadata?: Record<string, unknown>; // تُفلتر داخل AuditModule
};

مثال استخدام داخل Command Service

@Transactional()
async updateOrganizationUnit(id: string, input: UpdateInput) {
  const before = await this.repository.findById(id);
  const updated = await this.repository.update(id, input);

  await this.auditFacade.record({
    eventType: 'ORGANIZATION_UNIT.UPDATED',
    entity: { type: 'ORGANIZATION_UNIT', id },
    outcome: 'SUCCESS',
    changes: pickChangedFields(before, updated),
  });

  return updated;
}

الـFacade يكمّل actor/IP/requestId/correlationId من RequestContext؛ لذلك لا نكرر تمريرها من كل خدمة. أما معنى الحدث والكيان والتغيير فيأتي من Command Service لأنه الوحيد الذي يفهم العملية.

لماذا هذه الفهارس؟

تغطي أكثر أسئلة النظام شيوعاً: سجل tenant، تاريخ كيان، نشاط مستخدم، ونوع حدث خلال مدة. ترتيب created_at + id يدعم Cursor ثابتاً عند تساوي الوقت.

ما الذي لا نفعله الآن؟

لا نضيف GIN لكل JSONB ولا Partition شهرياً قبل قياس الحجم وخطط التنفيذ. كثرة الفهارس تبطئ الكتابة وتزيد مساحة التخزين.

JSONB بدون تضخم

// أفضل: الحقول المتغيرة فقط
old_values: { "status": "ACTIVE" }
new_values: { "status": "SUSPENDED" }

// سيئ: نسخ المستخدم أو الشحنة كاملة مع العلاقات والتوكنات
new_values: { "...fullEntity": "..." }

ضع حداً منطقياً لحجم السجل (مثلاً عشرات KB لا MB)، واستبدل القيم الكبيرة بوصف مختصر أو hash أو reference آمن.

09

كيف نقلل الطلبات والحِمل؟

المشكلة لا تُحل بالكاش وحده؛ تبدأ من شكل API والاستعلام.

في الـBackend

  1. Endpoint واحد: يعيد items وpageInfo، وsummary اختيارياً بدلاً من 3–5 طلبات متتابعة.
  2. Cursor Pagination: أسرع وأكثر ثباتاً من offset في الجداول المتزايدة.
  3. Projection: نستخدم select للحقول الظاهرة فقط، ولا نعيد JSON الكبير بقائمة الجدول؛ التفاصيل تُطلب عند فتح سجل واحد.
  4. لا N+1: actor snapshot مختصر أو join/batch واحد، وليس طلب user لكل صف.
  5. ETag: الطلب المتكرر لنفس الفلاتر يمكن أن يحصل على 304 Not Modified.
  6. حدود: default 25، max 100، ومدى زمني مطلوب للتقارير الثقيلة.

في الـFrontend

  1. Debounce 350–500ms عند البحث والفلترة.
  2. إلغاء الطلب السابق بـAbortController عند تغيير الفلتر بسرعة.
  3. Query cache حسب filters + cursor مع staleTime قصير 30–60 ثانية.
  4. Prefetch صفحة واحدة تالية، وليس جميع الصفحات.
  5. لا Polling افتراضي: زر تحديث؛ SSE لاحقاً فقط إذا كانت real-time ضرورة.
  6. تفاصيل عند الطلب: القائمة خفيفة، وJSON الكامل يظهر عند فتح drawer.

10

الأمان والخصوصية

سجل التدقيق نفسه قد يتحول إلى تسريب بيانات إن خزّنا كل شيء.

يُمنع تخزينه

  • password أو password_hash.
  • OTP وأكواد الاستعادة.
  • Access/Refresh tokens وAuthorization header.
  • Cookies وsession secrets وAPI keys.
  • بيانات دفع حساسة أو أرقام بطاقات.
  • محتوى الملفات أو Base64.
  • Request/response body كامل بشكل تلقائي.

سياسة Redaction

  • Allowlist للحقول المسموحة أفضل من blacklist فقط.
  • مُنقّح مركزي داخل AuditModule.
  • حد أقصى للعمق والحجم وطول النص.
  • إخفاء phone/email عند عدم الحاجة الكاملة.
  • اختبارات تمنع تسرب أسرار مع حقول nested.
  • الوصول للـAudit نفسه يُسجل كحدث حساس عند التصدير.

عدم العبث والاحتفاظ

  • Append-only: التطبيق لا يوفّر update/delete عاديين للسجلات.
  • صلاحية DB محدودة: مستخدم التطبيق يملك INSERT/SELECT المطلوبين، ولا يملك تعديل السجل إن أمكن تشغيلياً.
  • Retention: اتفقوا على 12 أو 24 شهراً حسب الحاجة القانونية، ثم archive مشفّر قبل الحذف.
  • Integrity لاحقاً: عند حاجة compliance قوية يمكن إضافة hash chaining أو تصدير immutable storage؛ ليس ضرورياً للنسخة الأولى.

خطة تنفيذ تدريجية

نقلل المخاطر ولا نبني بنية أكبر من الحاجة.

المرحلة 0 — قرارات

  • من يستطيع القراءة؟
  • مدة الاحتفاظ والأرشفة.
  • أول 5–10 أحداث حرجة.
  • سياسة فشل كتابة Audit.
  • الحقول الحساسة وقواعد الإخفاء.

المرحلة 1 — الأساس

  • Migration للحقول والفهارس.
  • AuditModule + Facade + Repository.
  • إغناء RequestContext.
  • Redactor مركزي وحدود الحجم.
  • ربط أول العمليات الحرجة داخل Transaction.

المرحلة 2 — القراءة

  • GET بفلترة وCursor.
  • صلاحيات Platform/Tenant.
  • قائمة خفيفة + تفاصيل عند الفتح.
  • ETag وfrontend cache/debounce.
  • قياس EXPLAIN وحجم response.

المرحلة 3 — حسب القياس

  • Outbox/worker للأحداث غير المتزامنة.
  • Partitioning عند أحجام كبيرة فعلياً.
  • Archive إلى storage غير قابل للتعديل.
  • SSE أو live updates إن طلبها المنتج.
  • تقارير أو dashboards.

خطة الاختبار

نجاح الـAPI وحده لا يثبت صحة Audit.

Unit

  • Redaction للحقول nested.
  • حساب diff.
  • توحيد event names.
  • حد الحجم والقص.

Integration

  • نجاح الأمر والسجل معاً.
  • Rollback يمسحهما معاً.
  • فشل auth يُسجل مستقلاً.
  • Idempotency يمنع التكرار.

Security & Performance

  • tenant isolation وIDOR.
  • لا أسرار في JSON.
  • EXPLAIN ANALYZE للفلاتر.
  • استجابة ثابتة مع 1M سجل تجريبي.

معايير قبول مختصرة

  • كل عملية حرجة متفق عليها تنتج سجلاً واحداً فقط.
  • السجل يحوي actor/tenant/event/entity/outcome/time/requestId.
  • لا يظهر password أو OTP أو token في أي سجل أو response.
  • Tenant A لا يستطيع رؤية سجل Tenant B حتى بتعديل query يدوياً.
  • فشل العملية داخل Transaction لا يترك success audit.
  • فتح قائمة 25 عنصراً لا يسبب N+1 ولا يعيد JSON الكامل.

قرارات يجب أن نحسمها كفريق

بعد الاتفاق عليها يصبح التنفيذ مباشراً وواضحاً.

نطاق النسخة الأولى

ما أول الأحداث؟ المقترح: auth، roles، tenant settings، organization units، shipment status/cancel.

سياسة الفشل

المقترح: العمليات الحرجة fail-closed داخل Transaction؛ الأحداث الثانوية تنتقل لاحقاً عبر outbox.

الاحتفاظ

12 أم 24 شهراً؟ ومن يملك قرار الأرشفة والحذف؟

من يقرأ؟

Platform Owner، Tenant Admin، ودور Auditor بصلاحية مستقلة.

هوية الفاعل

هل نضيف actor snapshot الآن لتجنب N+1 وحفظ الاسم بعد حذف الحساب؟ أو نكتفي بالـID مع batch join؟

حجم متوقع

عدد العمليات/اليوم وعدد سنوات الاحتفاظ؛ بناءً عليه نقرر متى نحتاج partition/archive.

القرار النهائي المقترح: نبدأ بـAuditFacade transactional + HTTP context collector + فهارس + Cursor API. نؤجل Outbox وPartitioning حتى تظهر حاجة تشغيلية مقاسة. بهذه الطريقة نحصل على موثوقية جيدة، لا نربط الموديولات بمستودعات بعضها، ولا نزيد عدد طلبات الواجهة بلا داعٍ.
وثيقة Offline قابلة للإرسال والفتح مباشرة بالمتصفح — أُعدّت اعتماداً على بنية المشروع الحالية. هذه وثيقة اقتراح ونقاش؛ لم تُجرَ عبرها أي تعديلات على كود التطبيق أو قاعدة البيانات.
